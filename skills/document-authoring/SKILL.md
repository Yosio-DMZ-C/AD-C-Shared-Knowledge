> **編集時のみ読む正本**：本Playbookの作成・改訂者が現在の理念・設計理由・更新手順を実取得する。文書を作る通常利用者に全文読解や共有投稿を求めない。

EDIT_REF_UPDATE_PLAYBOOK=https://github.com/Yosio-DMZ-C/AD-C-Shared-Knowledge/blob/main/docs/DEVELOPMENT_WORKFLOW_PRACTICES.md

## 1. 一行依頼から文書を完成する

`目的 → 文書の受け手・用途・必要情報を確定 → 既存テンプレート／正式資料を取得 → 原稿と読みやすい構成 → 必要ならアイコン候補選択 → 編集可能な文書を作成／更新 → レンダリング・読戻し → 実ファイルを渡す`。

**選択基準**：既存ファイルの修正なら元ファイルを作業コピーして、承認済みの文章・配置・画像・署名・アイコンを維持し、**依頼された差分だけ**編集する。新規文書なら、用途に合う見出し・本文・図表を先に作り、デザインは目的に従属させる。不要な画像・装飾・余白詰めはしない。保存先や形式の明示がなければ、利用可能な編集可能形式を1つ選び、その形式を伝える。重大な不足条件以外を質問で止めない。

## 1A. 一般読者向けブログ記事の冒頭（対象記事だけ必須）

**発動条件**：「ブログ記事を書いて／編集して」「解説・実証・体験を記事にして」など、一般読者が本文を読むための**解説記事・実証記事・体験記事**を制作するとき。WordPressを含む媒体に関係なく原稿の**記事タイトルの直後、本文で最初の見出し**を必ず `この記事のまとめ` とする。短いお知らせ・更新告知・イベント案内・単独の更新履歴・技術ログ・内部検収報告には自動適用しない。本人が適用を指定した場合はその指定を優先する。ブログの運用監視、投稿API／ツール開発、実際の投稿・公開操作は本節の対象外。

**「この記事のまとめ」の制作ルール**：
1. 冒頭30秒で、専門外の読者が「何が面白いのか／続きで何を読めるのか」をつかめる短い自然な読み物にする。**何をやった／何が大変だった／何ができた／なぜ面白い**の4要素を、身近な言葉で伝える。4個の機械的箇条書きにする必要はない。
2. 専門用語・ツール名・ログ・記事ID・実装詳細・検収表は原則として後続本文に回し、冒頭での重複説明を避ける。事実と期待を区別し、成功と書くのは検証済みの範囲だけ。
3. この節の中に**大きく見やすい図解を最低1点**置く。絵・複数の意味あるアイコン・矢印を中心に、具体的な道具と行動を少ない文字で示す。原稿段階で図解の構成と配置を指定し、完成原稿では実図を配置する。スマートフォン表示、日本語の欠字・切れ・コントラスト・代替テキストを実際の表示結果で確認する（未表示・未検査ならPASSと書かない）。
4. 図解制作は既存の[PPTX制作入口](../video-production-setup/SKILL.md#pptx資料制作採用済みキット再利用の1入口2026-11-10限定追補)／[素材仕様・表D](../video-production-setup/PRODUCTION_ASSETS_GENERAL_SPEC_v0.1.md)／案件ブランドを優先。必要なら編集可能なPPTXを原本とし、記事掲載用PNG等を派生出力する。公式ロゴ・確定素材は描き直さない。日本語の描画は共通のNoto Sans JP基準に従う。図解の内容も**実証済みの事実に限定**し、未実証の成功を視覚表現で補わない。
5. 節の**最後の一文**を次の原文で固定する。図解・補足・キャプション・追記はこの一文より前に置く。

**さて、次の項からは、実際に困っている/やってみたい‼︎人向けに詳しく説明していきます‼︎**

**後続本文の扱い**：元の詳細レポート、根拠、図表、実装手順、失敗原因、検証結果は削らず、まとめから自然につなぐ。確定済みの本文・画像・編集ロックは本人の変更指示なしに改変しない。今回の要件を、通常の報告書・文書や全ページのアイコン強制へ広げない。新しい承認・停止ゲートは作らない。

## 2. アイコンを使うときの共通の道具棚（最重要）

**人間が目で見て読む文書では、内容に合うアイコンを積極的に検討する**。重要な区分や行動が一目で伝わる適切な候補があれば、文字だけで済ませず少数を採用する。おすすめの置き所は、読み手が何の項目か一目で分かる小見出し、重要な注意点、1〜3工程の手順、チェック項目や資料の種別。**本文の代わりに記号だけを置かない**。契約書・公的文書・厳密な学術論文など装飾が不適切なものは無理に使わない。全見出しや全ページへの配置を標準化しない。

**既存素材の唯一の探索入口**：[制作素材一般仕様表の表D（PPT・文書共通アイコン探索）](../video-production-setup/PRODUCTION_ASSETS_GENERAL_SPEC_v0.1.md) → 必要時のみ[16点SVG早見シート](../../assets/ppt_icon_reference_sheet.svg) → [Lucide公式](https://lucide.dev/icons/) または [Tabler公式](https://tabler.io/icons)の**個別原本SVG**。見本シートを切り抜いて編集用原本としない。表Dのテキスト名を先に読み、形状比較が必要なら1枚のSVG見本を見て、最終的に公式の個別アイコンを取得する。OCRを常時起動しない。

| 文書の意味 | 探索する候補（既存表Dの例） | 置き方 |
|---|---|---|
| 資料・調査・確認する | `search`（Lucide） | 小見出しの左に1つ。検索作業の項目に |
| 書く・改訂する | `pencil`（Lucide） | 手順の「編集」ラベルの前に |
| 確認・完了 | `check`（Lucide） | 実際に確認済みの項目、チェック表に |
| 期限・予定 | `calendar`（Lucide） | 予定欄の補助。日付を文字で必ず併記 |
| 保存・受渡し | `download`（Lucide） | ファイルの受渡し説明で必要なときに |

**描画の原則**：1つの文書で同系統のアイコン群（例：Lucide）に統一し、適用サイズと線の太さ、色を揃える。見出し近くでは目安14〜18pt相当、本文幅や行間を崩さない最小サイズにする（固定の義務サイズではない）。モノクロ印刷・縮小・背景とのコントラストでも識別可能にし、意味を日本語文字で併記する。アクセシビリティ上必要な場合は代替テキストを付ける。アイコンの色・配置は既存ブランドの採用済み値と本人の指示が優先。

**形式別の挿入**：Word `.docx` は公式SVGの挿入が実際に扱える場合はそのまま、対応不明・レンダリング不一致なら**公式SVGを保持したうえで高解像度PNGに変換して挿入**。文書の本文・表・見出し自体は編集可能のままにする。Google DocsやWriterでは対応する画像挿入方式を使い、編集可能形式とアイコンの画像性を区別する。アイコンを文字フォントの記号で代用して別PCで欠字になることを避ける。

**ライセンス**：LucideのISC、TablerのMIT等について、使用した**個別原本の出典・版・ライセンス表記と必要な著作権通知**を確認して保持する（内部作業記録／文書末尾のクレジット欄／配布物に同梱するNOTICE等、適切な形）。「無料だから表示不要」と決めつけない。外部素材・企業ロゴ・本人の採用済みイラストは無断生成で置換しない。配布形態に合うライセンスが不明ならその素材のみ採用保留とする。

## 3. 文書の編集・完成ルート

1. **原稿と見出し**：まず目的に合う見出し構成、読み手に必要な本文、表・図の情報を作る。引用・重要数値・日付などは実際の根拠と区別し、ソース不明を推測補完しない。Wordの「見出し」スタイルなど意味構造を維持する。
2. **人間向けの視覚的な手がかり**：見出し・手順・注意点で読み取りを助ける候補があれば、表Dから少数の公式アイコンを取得して積極的に挿入。最小限のアクセントとして使い、通常の報告書を無条件にポスター化しない。ユーザー指定のブランド・紙面デザイン・画像ロックを守る。
3. **出力と実検収**：`.docx` など編集可能な現物を保存・再取得し、本文・見出し・表・画像実数・元データを確認。実際に利用可能なレンダラで全ページまたは変更ページをPDF／画像化して、**日本語字形、図と文章の回り込み、余白、切れ、ページ境界、アイコンの意味・表示サイズ**を確認。不具合は該当ページだけ修正して再確認。
4. **引渡し**：実ファイルへのリンクを提示し、必要時だけPDFなどの派生物を添える。`ファイル生成／再読込／描画確認／Wordアプリでの実機確認／別AI独立再現` を別状態で記録し、推測のPASSを書かない。本人が日本語で内容・編集箇所・変更しない場所を理解できる短い説明を付ける。

**実装手段は固定しない**：Wordを直接編集できる接続ツールがあればそれを優先。ファイルを扱う実行環境では `python-docx` 等で本文や表を編集し、SVG→PNGを適切な画像変換機能で行ってもよい。独立した新しいPythonインストールや画像生成モデルを利用者へ強制しない。図形・画像が必要と判断した場合でも、文書の正式素材とアイコン集は別。

## 4. 最小利用試験と採用状態

**試用ケース**：「AD&Cの作業を3段階で説明するWordのA4・1ページ文書を作って」。既存表Dから `search`／`pencil`／`check` を選択し、公式SVGを取得、画像として挿入、本文編集可能なDOCXを保存・再読込・描画する。アイコンのある見本と、アイコンなしの文章のみの場合で読みやすさを確認し、**人間の実評価・Word実機・別AI初見再現は各々実試験前ならNOT_RUN**とする。既存共有KBにあるアイコン参照とPPT制作Kitを勝手に改変しない。

**最小試験の今回実測（2026-11-10）**：Lucide公式リポジトリから個別 `search.svg`／`pencil.svg`／`check.svg` とLICENSEを実取得し、PNGへ変換してA4・1ページの `.docx` に3点挿入。本文・見出し・手順の編集可能性、ZIP/DOCX再読込、挿入アイコン3点の代替説明、LibreOfficeからの**1ページPNG描画**を確認した。描画画像を実見し、切れ・日本語欠字・重なりなし。アクセシビリティ静的監査（high/medium/low）=0/0/0。**これはこの実行環境の機械・目視試験PASS**であり、Microsoft Word実機・Google Docs変換・一般利用者の改善効果・初見の別AI再現は未検証。サンプルDOCXは試験用であり、個人／シリーズの正式テンプレートには採用していない。ライセンス情報は試験成果のNOTICEで同梱。
