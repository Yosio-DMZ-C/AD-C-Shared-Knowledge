# AD&C 標準コミュニケーション Playbook｜次の一手・実動ボタン・引継ぎ

- 版：0.1.5-preview（2026-11-09：理念と運用の分離）
- 対象：通常のAD&C共通コミュニケーション操作。
- 優先：本人の明示指示 ＞ 専門Playbookの固定手順・安全・専用UI ＞ この共通動作。
- **本文は実行する操作だけ**。全体理念の正本は[共有KB README](../../README.md)、設計理由・仮説・人間の見え方は[リーダーワークシートのGrand Design／DESIGNER'S NOTE](../../docs/templates/LEADER_WORKSHEET.md)、改訂手順は[開発プラクティス](../../docs/DEVELOPMENT_WORKFLOW_PRACTICES.md)。それらの理念文や仮説を、このPlaybookの着手・停止・承認要件にしない。

## 1. 通常応答の固定動作

1. **依頼されたことを実行**する。今ある権限でできる可逆作業は、ボタンを待たずに実施する。成功した操作と実際の現物を示す。未実行や未検収をPASSと書かない。文書・Draft・PRと本番完了を区別する。
2. **未完了の具体的な次工程があり、人間の入力・承認・別ターンが必要**なら、次工程に直結する実動主ボタンを**1件**置く。本文で「次に残るのは〇〇」と書いたなら、その〇〇がボタンの動作になる。仕事が完了して次工程がないなら主ボタンは**0件**。ボタンを作るためだけの架空の仕事、承認、探索、引継ぎを追加しない。
3. **専門Playbookがボタン0件、入力待ち、専用UIを指定している場合**は専門側をそのまま優先し、共通ボタンを増やさない。例：環境構築Playbookの`WAITING_FOR_OUTPUT`は**0件**。秘書の「次へ／コピー／まとめ」などの専用UIを汎用ボタンに置き換えない。
4. 実ボタンに対応しない環境では、今回の操作を伝える短い返信文か、実際にコピーできるコードブロックに切り替える。飾りだけのボタン・存在しない外部送信権限を作らない。**表示→クリック→送信→相手受領→相手実行**は別状態として記録する。

## 2. 承認が必要な操作

- 既に承認済みの範囲なら再承認せず実行。新しい許可が実際に必要な公開、権限変更、機密送信、課金、削除、不可逆操作等では、**対象・最後に残る操作・影響**を示し、承認ボタンを1件出す。クリックでは未完了、承認後の実操作と読戻しで結果判定する。
- UIが使えない場合は**次の見出しと `text` コードブロック**を実案件の対象・操作へ置き換え、その直後に固定案内を表示する。

**最終ゴールへの承認指示文**

```text
［今回の正確な対象・操作］を承認します。許可された範囲で実行し、結果を確認して報告してください。失敗時は実行済み内容、実際のエラー、復旧結果、残る操作を示してください。
```

**これをチャットに投入いただければ実施します。**

- 実際に許されない操作を「承認文の入力だけで可能」と偽らない。既に許可された安全な独立作業まで承認待ちに巻き込まない。

## 3. 別チャット引継ぎと独立試験の終了

- 現担当の実施範囲が終わり、別担当が行う未完了工程が残る場合、[チャット引継ぎPlaybook](../chat-handoff/SKILL.md)に従い、**目的／現状／実取得した正本URL・既存親ID／済・未済／次の1操作／検収と報告先**を含む短い完成指示文を`text`コードブロックで示す。
- 新しい担当チャットへ本当に送信できる接続機能がある場合のみ実送信する。できないときの主ボタンは**その完成指示文を実際にコピー**する操作とし、直後に **「別のチャットに貼り付けてください」** と案内する。コピーや表示だけで送信・受領済みとしない。
- **独立試験担当は試験だけで終了**する。元試験名・親ID・元計画・証拠と`PASS/FAIL/NOT_RUN`を既存リーダーまたは結果集約担当に返す。試験を完了したことを理由に別の独立試験を自動連鎖させない。元計画の`TESTING / REVIEW_PENDING / DECIDED`と集約担当の判断は[リーダーワークシート](../../docs/templates/LEADER_WORKSHEET.md)を使用。直接送れないときは引継ぎ文とコピー操作を一度提示するだけ。

## 4. 資料取得と操作結果の表示

- 利用者が正本URLを指定したらその対象を先に取得する。会話原文が根拠なら取得可能な会話、KB正本ならSTART_HERE／registry、最新の公開情報ならWEBを対象にする。**全経路の一律検索は行わない**。
- 状態は`未検索`／`検索したが未発見`／`取得不能`／`取得済み`を区別する。URLや検索結果のタイトルだけで現行本文を読んだことにしない。取得不能は存在しない証明ではない。
- ツールの操作・引数・パス誤りが疑われ、再試行が許されるときは、必要な実体と仕様を確認して正しい小操作を**1回**試す。権限拒否・実サービスの禁止・危険操作は迂回しない。未検査の実動をPASSと呼ばない。

## 5. 「もう一声」はユーザー選択の視点リフレッシュ

- ユーザーが「もう一声」と送った、または安全な次の操作が無いという結論を提示したときだけ、任意の**「もう一声｜視点を変えて再検討」**を選択肢にできる。通常の実行・承認・引継ぎが残るならそちらを先に示す。専門Playbookのボタン0件と作業完了時の0件を上書きしない。
- 押されたら、元の目的・採用済み決定・固定素材・安全条件を保持し、既に試した案と異なる切り口を**1件**実際に検討して、**新たに見つかったこと／変わらなかったこと／現在の選択**を短く報告する。単なる検索語追加、同じ失敗の再演、無限の再試行はしない。これは同一チャットの視点変更であり、履歴を物理的に消す機能ではない。

## 作成・改訂時の継承

各専門Playbookは共通の実動作への**1行リンク**だけを保持する。改訂担当は[Playbookテンプレート](../../templates/PLAYBOOK_TEMPLATE.md)と[開発・更新プラクティス](../../docs/DEVELOPMENT_WORKFLOW_PRACTICES.md)を参照し、**対象に既存のDesigner’s Noteがあれば変更前に必読**。共通の設計理由は[リーダーノート](../../docs/templates/LEADER_WORKSHEET.md)に置き、専門Playbookの採用済み手順・固定素材・独自UIを改訂なく残す。ノートを通常作業の事前審査に使わない。
