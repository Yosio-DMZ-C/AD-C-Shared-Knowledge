## PJ・定例の管理操作に限り「計画正本の特定」が標準必須

組織共有データを扱う場合に限り、対象組織の正式標準・分類・ACL・保存先を操作前に確認する。閲覧・検索・軽微な文書訂正は、許可された対象資料と該当専門Playbookへ直接進み、PJ分類・WBS参照／更新・新規台帳を要求しない。PJ・定例の管理操作だけ以下へ進む。個人領域の作業には本分岐を適用しない。境界を越える移動は提供元と受入側の双方の許可・条件が確認できた場合のみ実施する。

**対象組織のKBを使って、PJまたは定例業務の実行・進捗更新・委任・成果登録を行うときは、最初に該当業務の計画正本を1件特定する。** この参照を省いてAIが独自のWBS・定例タスク・進捗台帳を生成しない。既存の組織正式標準と権限を最優先し、本人が既に指定した正本があれば再探索を繰り返さない。単なる資料閲覧・検索・軽微な誤字訂正には計画書の新規作成やPJ分類を強制しない。

| 業務区分 | 正本の役割と更新対象 | 同じ情報を重複生成しない方法 |
|---|---|---|
| **PJ（期限・完了条件のある仕事）** | 採用済みPJ計画／1つのWBS・既存タスク管理先。成果物・工程・担当・期限・依存・検収 | `PJ_ID` → `WBS_CANONICAL_REF` → 既存`TASK_ID`へ戻る |
| **定例（繰り返し維持する仕事）** | 採用済み業務定義・周期・担当・実行手順・結果記録。毎回の成否、例外、次回予定 | `ROUTINE_ID` → `ROUTINE_CANONICAL_REF` → **実行回を識別する既存記録**へ戻る |

**どちらも計画は必要だが、同じWBSに押し込まない。** 定例業務がPJの中にある場合でも、必要なら元PJ／マイルストーンへリンクするだけで、定例側の正本や実行記録をWBSへ二重転記しない。PJは完了するが、定例は終了・改訂されるまで周期的に続く。定例の結果から新しい期限付き改善PJが必要になったときだけ、組織の既存管理手段と権限でそのPJを扱う。

**計画正本が見つからない場合**：`START_HERE`／既存Project・Area Context／registry／組織の承認済み管理ツールを調べ、候補と未確認を区別する。計画を欠く実業務を放置しないが、**その場で新しい管理ファイルを必ず作るという意味ではない**。組織の管理責任者・権限を確認し、既存の保存先に最小計画を作成／結び付けられるなら1件だけ作る。競合する複数正本があれば勝手に選び直さず、競合書込だけ止め、許可済みの調査・独立作業を進める。計画の実取得、実行、結果の保存は別々に確認する。

## PJの最優先規則｜1 PJ・1管理正本。WBSを勝手に増殖させない

**PJごとに管理上の唯一の正本（`WBS_CANONICAL_REF`）を特定する。** WBSは成果物の分解、日程・担当・依存・実行状態はそのWBSに紐づく既存タスク管理情報。既存のSharePoint／Microsoft Lists／Project／GitHub Issues／Spreadsheet／WBS Markdown等で、**組織が実際に指定した管理先を正本**とする。方式をAD&Cが勝手に変更しない。

1. 最初に対象組織の権限内で`START_HERE` → 既存PJのProject Context・`BUILD_PLAN`・registry/索引 → 組織の正式タスク管理先を辿る。既存のWBS・PJ ID・タスクID・責任者・採用版を探す。**新しいWBSを生成する前に現存する正本を確認**する。
2. 既存の正本が1件なら、そこを参照・権限内で更新する。Project Contextに正本参照が未記載で書込権限があるときは、**その既存Contextへ正本のID／リンク・管理責任者・確認日だけ補う**。WBSの全文コピー・別の進捗表は作らない。
3. 複数のWBSらしいものを見つけたら、**複製・統合・選択の推測をしない**。組織の正式指定・管理者・更新履歴から正本を確認し、判断不能なら候補と衝突箇所を責任者に1点だけ示す。確認まで対象のWBSの**競合する書込だけ保留**し、読取・他の仕事は継続する。過去版・個人作業コピーを正本へ昇格させない。
4. 正本が無い新規PJだけ、組織が指定する既存管理ツール・既存テンプレート・管理者の新規作成権限を確認して**初めて1件**作る。新規作成と同時にその1件を既存Project Contextへ結び、再実行時は同じPJ IDで既存正本を再取得する。承認・権限不足なら勝手に新作せず、既存PJの文書作業等を進める。
5. 読取専用の表示・一時的な抽出・個人メモを作る場合は必ず`VIEW / SNAPSHOT`と明示し、更新用WBSや並行正本として扱わない。組織のシステムが一意制約・認可・競合検知を提供するならそれを利用し、**Playbookの文章だけで重複作成を技術的に阻止できたとは主張しない**。

## 管理の最小仕様｜既存フィールドを再利用

新たな列・必須フォームを全組織に強制しない。既存WBS／タスク管理先に次の意味を保持し、欠ける要素を表示時に補う。仕事に必要な単位で十分。

| 管理対象 | 最小の意味 |
|---|---|
| PJ | `PJ_ID`、一意の`WBS_CANONICAL_REF`、PJ責任者・閲覧／更新権限、最終確認時点 |
| タスク | 同じPJ内で安定した`TASK_ID`、成果物／完了条件、責任担当、期限、状態、必要時の依存先 |
| 完了の証拠 | 成果物・検収・利用可能になった結果の既存リンクまたは記録ID。単なる「報告済み」「AIが生成した」は検収済みDONEではない |
| 未完了の現在地 | 停滞要因、次の実操作・判断先、更新時点。実施済／未検証／未実施・`DONE_WITH_ISSUES`を区別 |
| 貢献の出典 | タスクの責任担当と、実際に成果・支援・レビューを行った**貢献者**を別軸で辿れる既存記録 |

`DONE`／`IN_PROGRESS`／`BLOCKED`等は例示。組織の既存ステータスをそのまま使い、集計時だけ読み替える。期限や担当が未確認なら空欄／`UNKNOWN`、未登録をゼロ件や本人の怠慢と解釈しない。

## 定例業務の最小仕様｜1定例・1計画正本と、回ごとの実績

**「毎日点検」「週次のレポート」「毎月の棚卸」「半月次レビュー」などは、PJのWBSを毎回作らない。** 定例業務の定義・担当・周期・対象範囲・成功条件・承認済みの実行手順・停止／取消条件と結果の保存先は、組織で既に採用した手順／定期Task／Area Context等の**一つの管理正本**を参照する。各実行回は同じ定例IDにぶら下がる事実であり、別の定例計画ではない。

| 項目 | 必要な意味・扱い |
|---|---|
| 定例の唯一の参照 | `ROUTINE_ID`＋`ROUTINE_CANONICAL_REF`（組織の既存ID・保存先が優先） |
| 計画 | 業務目的、周期／起動条件、担当・代行、対象、手順・Playbook、完了条件、結果の記録先、次回予定の算定方式 |
| 1回の記録 | `ROUTINE_ID`＋**対象期間／実行回ID**（既存のJOB ID・スケジュール発火ID等を再利用）、実施時点、担当、結果、証拠、例外、次回までの残件 |
| 状態の区別 | `SCHEDULED`／`IN_PROGRESS`／`DONE`／`DONE_WITH_ISSUES`／`UNKNOWN`／`MISSED`等は表示上の例。既存システムの値を上書きしない |
| 完了確認 | 「通知済み」「起動済み」「結果保存済み」「管理者が受領」は別。実行ログが読めない回は未確認とし、未実行とも成功とも決めつけない |

1. **既存定義を優先**：定例の自然文から既存`ROUTINE_ID`／正式な実行元／直近の履歴を実取得。新しいAutomation・JOB・定期タスクを無断で作らず、既存の予定・権限を変更しない。
2. **同じ回を二度実行しない**：対象期間や既存の実行回IDで先行実行・処理中・成功・UNKNOWNを照合。特に配送・削除・課金・外部送信など副作用がある作業は、結果不明を未実行と決めつけて再実行しない。衝突は該当する回の記録だけ照合し、他の独立業務は続行。
3. **成果を元の場所へ返す**：実行担当は既存の結果保存先で、その回の成否・現物リンク・異常・次の一手を読戻し可能に残す。定例の定義そのものは周期ごとに新規作成しない。予定変更・担当交代・手順改訂が正式に決まった場合だけ同じ正本を更新する。
4. **定例の管理指標**：指定期間内の**予定された回数を分母**とし、検証済み完了数・期限超過／欠測・異常・未処理残務・担当負荷を区別する。PJの「全タスク完了率」と定例の「実施達成率」を無条件に合算しない。予定回数が不明なら分母不明。
5. **PJとの接続**：定例の結果がPJ成果を支える場合は既存`PJ_ID`／`TASK_ID`を結果記録から参照するだけ。定例実行回を同じPJの新WBS行へ周期ごとに増設せず、同一成果をPJと定例で二重に数えない。

## KBの活動・成果をPJ・定例の計画へつなぐ最小タグ

**KBの全ファイルに個人タグを必須化しない。** PJ・定例の成果・判断・支援に関わる**既存の更新記録／変更履歴／成果物メタデータ**に、既にある項目が使えれば次の意味だけ関連付ける。以下はPJ例で、定例なら`PJ_ID / TASK_ID`を`ROUTINE_ID / EXECUTION_ID`に読み替える。

```text
PJ_ID=PJ-例
TASK_ID=T-例
CONTRIBUTOR_ID=組織内の安定ID（表示名でなく既存の認証・担当マスタへ接続）
CONTRIBUTION=deliverable | fix | review | support | knowledge
EVIDENCE_REF=既存の成果物・差分・受入記録への参照
# 定例の場合: ROUTINE_ID=定例の既存ID / EXECUTION_ID=既存の発火・実施回ID
```

- **入力最小化**：PJでは`PJ_ID`・`TASK_ID`、定例では`ROUTINE_ID`・既存の実行回ID／対象期間があれば、正本と成果を結合できる。誰の貢献かが記録に存在するときだけ`CONTRIBUTOR_ID`と役割・種類を付ける。Git/Drive等の変更履歴、既存の担当・レビュー情報が利用できれば再入力しない。組織が既に使うタグ名・イベント形式を優先し、上記の英語キーを新しい全件必須列にしない。
- **担当と貢献を混同しない**：タスクの責任者（`owner`）・実作業者（`contributor`）・レビュー担当・記録者は別。複数人の支援を記録できるが、同一成果を人数分の完了タスクに複製しない。担当者名を本文で言及しただけでは実績の証拠にならない。
- **実証と申告を分ける**：検収済み成果、本人・同僚の申告、AIが推定した関与、監査ログを区別する。書き込みアカウント＝実際の考案者とは限らず、AI作業はAI利用・人間の指示・人間の検収を区別して表示する。紐付け不能は`UNKNOWN`、個人実績を推測で帰属させない。
- **既存履歴が根拠**：同じ成果の複数報告を別の貢献件数として重複加算しない。根拠の一意ID・時刻・成果物リンク等が実際にあれば利用する。貢献のためだけの報告書・別人員台帳・自動提出は作らない。

## 現場の実行・組織長の判断（PJと定例を横断）

1. **現場担当**：専門Playbookで実務を進め、完成物と検収結果を既存の保存先に置く。PJなら唯一のWBSの該当`TASK_ID`、定例なら唯一の定例正本に紐づく該当実行回だけを権限内で更新し、関連するKB履歴に成果・貢献の根拠を結ぶ。更新後は該当行・実行回・成果だけを読戻す。
2. **進捗の取得**：管理者が「現在地を見せて」と言えば、各業務の唯一の計画正本と必要な結果履歴を取得する。PJはWBSの完了／未完了・期限・依存・停滞、定例は指定期間の予定回数・実施確認・未実施疑い・異常・残務を**別集計**で示す。取得できない範囲は`NOT_RUN`、未集計を0件としない。複数の作業コピーから勝手に件数を足さない。
3. **貢献の取得**：指定された期間・PJ／定例・本人閲覧権限の範囲で、`TASK_ID`または`ROUTINE_ID`と実行回に結びついた既存の成果／改善／レビュー／支援を、人物別に**事例・役割・根拠リンク**で示す。成果の難易度、支援、未完了でも有意な改善を区別し、数値の単純比較を人物の価値にしない。
4. **組織長の出力**：短く「PJの進捗／定例の実施・異常／進んだ成果／停滞・未処理／担当の負荷偏り・支援／本人判断が必要なこと／次の一手」を示す。読むためのダッシュボードは元の計画正本・実行履歴・KBの**派生ビュー**であり、新しい編集可能な進捗正本にしない。定期化は組織が元から使う会議・報告周期や利用者の明示希望があるときだけ。
5. **終了・再開**：PJなら既存ContextのWBS参照と未完了タスク、定例なら既存の定義参照と直近の実行回・次の予定を確認し、必要な次工程だけ元の記録に保存・読戻す。別チャット／別AIでは**同じ業務ID→同じ計画正本→該当タスクまたは実行回**へ復帰する。再開の実行・相手受領は別検査。

## 人の評価と組織の情報を守る

**貢献の可視化 ≠ 人事評価の自動採点**。件数、更新頻度、AI生成量、チャット数、見かけのリードタイムだけで個人ランキング・報酬・査定を決めない。成果の質、難度、役割、助力、環境、評価期間、本人の説明、管理者の判断を必要に応じて確認する。データ欠落は「貢献なし」としない。本人に見せる前に組織内の正式な人事方針・プライバシー・閲覧権限に従う。

組織データは当該組織の正式な分類・ACL・保存先・持出／持込ルールが優先。個人情報・人事情報・非公開WBSは公開共有KBや外部AIへ無断転載しない。全社員の行動ログ監視・私的チャット収集・不要な人物プロファイル生成を既定にしない。目的に合う範囲の既存証跡だけ利用する。

## 小さな検証ケース（設計テスト。実組織運用ではない）

- **A｜既存WBSが1件**：Project Contextが組織公式WBSを参照。別AIが同じPJを管理する依頼を受けても新WBSを作らず、同じIDへ到達し更新は権限内の対象タスクだけ。検査：正本参照が一本、同じタスクID、重複書込0。
- **B｜共同成果**：責任者A、実装B、レビューC。KB記録に同一`TASK_ID`でBの成果とCのレビューがあり、Aの責任担当を保持する。検査：完了タスクは1件、貢献はB・Cの根拠付き記録、貢献者数を完了件数と混同しない。
- **C｜WBS候補が2件**：似たファイルの双方に進捗。組織の指定が不明なら自動で3つ目を作らず、競合更新をせず、誰に正本確認が必要かを示す。検査：WBS新規作成0、既存の他作業は継続。
- **D｜証拠のない人名タグ**：AIが本文から名前だけ検出。成果・役割の確認なしでは貢献確定せず、未確認のまま表示する。検査：自動人事点数0、誤帰属0。
- **E｜週次点検の繰り返し**：既存の定例正本1件、週ごとの実行記録2回。AIが同じ週を再依頼されても新しい定例計画・WBSを作らず、既存回の成否を調べる。検査：計画1件、既存実行回2件、重複生成0。
- **F｜定例の実行結果がUNKNOWN**：期限を過ぎた発火記録はあるが成果が見えない。無確認再実行せず結果先を照合し、組織長には未確認1回として報告。検査：誤DONE0、無確認の副作用再実行0。
- **G｜PJと定例が同じ成果に寄与**：PJのWBSと定例点検の結果を相互参照し、1つの成果を二重集計しない。検査：PJ完了率と定例実施率を別分母で表示。

## 人間向けHTMLダッシュボード（2026-11-20 共通生成方式を採用）

PJ・定例の読みやすい報告が必要なときは、[HTMLレポート制作Playbook](../html-report/SKILL.md)と実在する[Python生成器](../html-report/render_report.py)を**任意の表示手段**として使える。PJ=`kind=project`、定例=`kind=routine`。入力は**既存の正本から実取得したID・対象期間・実績・証拠・次の一手のみ**。HTMLをWBS・業務定義・実行結果の更新正本にしない。PJ完了率と定例の実施率は分母を分け、実行UNKNOWNを勝手にDONE/未実施へ変換しない。

利用権限・Python実行環境・HTMLの認証付き描画先は組織が決める。公開リポジトリに社内の個人情報、非公開WBS・実績、私的URLを配置せず、実社内受入は独立に検証。Pythonが使えなくても既存の管理作業・日本語報告は継続する。

## 結果の出力・次の一手

通常の管理応答は **「PJ・定例の計画正本と確認時点／PJ進捗と定例の実施状況（別集計）／担当別の未完了・依存・異常／根拠付きの貢献／組織長が判断する最小1点」** の順で簡潔に。閲覧できない範囲・古い更新・未検証を明記し、成果の読戻しと組織運用での実効果を区別する。人の作業を管理するための会議・報告制度・別WBSを増やさず、問題があれば元のPJ IDと実タスクへ戻して最小修正する。

設計上の限界：**このPlaybookだけでは複数AIの同時書込・WBSや定例業務定義の一意性・定時実行の重複防止を機械的に保証しない**。実運用では組織のタスク管理／スケジューラーが提供する一意ID・書込権限・競合検知・版履歴・実行ログを使用する。正式Active配布・異なるAIによる実組織のWBS／定例更新・実際の個人貢献集計は独立に検証する。
