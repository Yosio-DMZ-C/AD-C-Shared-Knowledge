# AD&C Shared Knowledge（旧AgentOS-C Shared Knowledge）

**AD&Cはアジャイルで実施する。Draftは本人が明示指定したときだけ作る。** 既定のゴールは使える成果物・実運用。許可済みの小さな実装→実測→必要な修正→保存・読戻し→次の一手まで進め、Draft保管で完了にしない。失敗・未検証は実態に応じDONE_WITH_ISSUES／NOT_RUN等で既存案件に残し、必要な担当に委任する。既存のDraft表記は過去の状態として保持し、自動で正式採用・本番公開・PASS扱いしない。本人の指示と専門安全条件を優先し、公開・削除・課金・機密送信・危険な不可逆変更は該当操作だけ制限する。


人生の重要な場面で、主要な議論・主張・根拠・反論を比較できるようにし、調べる時間を短縮する公開共有知の基盤です。最上位の目的は、本人のより良い選択を支えることです。

> **AD&Cの宣言｜完成形のない仕組みで、完成する仕事を増やす。**
> **アジャイルは理念の実行原則。本人の明示指定がない限りDraftは作らない。** 小さく実物を作り、実測で直し、使えるところまで届ける。終えられない場合は途中成果・問題・次の一手を残し、Draft棚で仕事を失踪させない。
> **小さくするのは完成の範囲であって、完成度ではない。** 最初から最後までつながり、実際に使える最小の成果を完成させ、その動作を観測して改善する。部品ごとの検証は必要な手段だが、動かない部分検証を積み上げただけでは成果の完成と数えない。
>
> 人もAIも不完全で、使う環境も変わり続けます。AD&Cは、完璧な論理体系や万能のAIを完成させるのではなく、**自然言語で既存のAI・知識・道具をつなぎ、安全・機能・分かりやすさ・人間の時間の釣り合いを、その都度実物で確かめて改善し続けるシカケ**です。
>
> **プレイヤー最優先｜Playbookは管理のためではなく、現場で使って成果を出すための道具。** 使う人と作業担当AIが、その場のPlaybook本文を読んで進められることを第一に設計する。短い共通実行手順は各Playbookの該当箇所に直接載せ、更新・差分・一括同期の手間は作成・更新側で引き受ける。現場に共通手順へのリンク巡回や余分な事前質問を強いない。採用済みの専門条件と安全・権限は守る。
>
> **AI・サービス非依存｜究極の柔軟性を保つ**：AD&Cの知識・判断・Playbookは、**人間にもAIにも読める自然言語（日本語のMarkdown等）**を主軸にし、繰り返し正確に動かす処理には **Python（`.py`）など世界中で広く使われる移植しやすい技術**を優先します。Manus・ChatGPT・Codex等の便利な独自機能は、使える人が選べる実行手段として積極的に借りますが、**目的・入力・出力・採用済み決定・成果物・再開方法は特定サービス内だけに閉じ込めない**。Pythonや特定AIを全員へ強制せず、環境が変わっても別のAI・道具で続けられる余地を残します。
>
> **仕組みに最終完成はなくても、個々の仕事には完了条件があります。** 「できた」は成果物・保存・読戻しで確かめ、「できなかった」は原因と次の手段を残します。誤りや不完全さを放置する免罪符にはしません。
>
> この小さな改善を重ね、**人の選択と暮らしを助け、社会に価値を広げることを目指します。** 成功率・時間削減・生活の質（QOL）への効果は、実測していない限り実証済みとは言いません。背景と開発判断の基準は[開発リーダー正本のグランドデザイン原則](docs/templates/LEADER_WORKSHEET.md#adc-grand-design-engineering-principle-approved-2026-11-04)を参照してください。


**読んで使うだけでも参加できます。共有知の更新への協力は任意です。** 個人の相談、利用履歴、健康・家族・購入情報を提供する必要はありません。

### 全利用者へ：定期実行と自動委任は「使っているAIの機能」で判断する

**AIに仕事を渡すたび、人間が指示文を運ぶ必要はありません。** 予定の時刻・条件で起動できるAIなら、必要に応じて「元の案件へ指示を保存→定期実行が拾う→使えるツールで仕事を進める→結果を元へ戻す」という自動配信・自動実行の方式を**利用者にも提案**できます。繰返し、待機、複数担当の引継ぎがあるときに役立つ選択肢です。

ただし、**定期起動、保存先への読書き、他AIへの送信、実作業の実行は別の能力**です。そのAIの製品・契約・接続先・権限で実際にできる部分だけを使い、単なる通知や登録を実受領・完了と偽りません。既存の許可済み経路は再利用し、必要な新規設定は本人の選択を経て行います。実行環境が足りなければ可能な部分だけ自動化し、手動の受渡しを最小限にします。**全員にChatGPTやAD&C開発専用のtmpを要求しません。** 詳細な条件分岐は[標準コミュニケーションPlaybook §3](skills/communication-navigation/SKILL.md)を参照してください。

**入口から実行Playbookへの一本化（既存KBだけで運用）**：

1. **目的から選定**：自然文の完成目標を読み、上表と必要時の既存索引から主担当の専門Playbookを**原則1本**選ぶ。本人の明示指定、対象組織の正式標準、実取得した個人KBの採用済みカスタムPlaybookを優先する。「直して」と「3Dモデル／PPT」が同時に出る場合は**3D／PPTの専門Playbookを主担当**とし、ループ方式は必要なら補助として使う。該当なしなら通常の仕事を継続し、無理に専門手順を選ばない。
2. **現行正本を実取得**：選定した対象の実在URL／パスから本文を**実際に読み**、適用条件・ID・版・採用状態・利用上の制限を確かめる。カタログにないDraft／試用本文は手動参照できても正式Active配布・自動導入ではない。個人版が採用済みの場合はその既存版を運用正本として扱い、共有側との差分や撤回情報を必要時だけ確認し、勝手に更新しない。取得失敗なら未取得と示し、利用可能な添付・既存KB・通常手段で可能な仕事を進める。
3. **主担当を固定**：本文を取得し案件に適合したら、その作業の主担当は1本に固定。作業中に単語だけで別の主Playbookへ乗り換えない。必要なツール・人間用ガイド・標準コミュニケーション・ループ方式・別分野の専門手順は**主担当から必要時だけ呼び、責任と再開の入口を分散させない**。本人が目的を変更、現行正本が不適合、適用制約が変化した場合だけ選び直す。
4. **既存案件へ再開情報を置く**：継続案件で書込権限がある場合は**既存の `BUILD_PLAN.md`／Project・Area Context／案件の現行記録**に、短く「依頼目的／主PlaybookのID・現行参照先・版（取得できればGit commitまたはblob）／既済成果と現物リンク／未検証・問題／次の1工程／状態」を追記・読戻しする。新規ルーティング台帳・二重Runbook・Taskを作らない。保存先・権限がない場合はこのチャット内の短い引継ぎ情報として示し、**永続保存済みと偽らない**。
5. **完成または再開**：検収・保存・読戻し・結果の出力と次の一手は主担当の実行条件を優先する。途中再開時は既存案件の主Playbook指定と現在地を先に読み、**同じID・採用版・本文へ復帰**して未完了だけ進める。旧DONEを再実行せず、取得／相手AIの受領／実再開を別々に判定する。案件完了後の新しい依頼は再選定する。

これは**日本語の実行契約**であり、ChatGPT等が共通入口を自動取得できること、別AIでの無条件の自動選定・実再開が動作済みであることを意味しない。全件全文取得・毎回答の選定・固定の管理項目追加・別Task作成を要求しない。

**実行順序**：`自然文で目的判定 → 主担当1本の選定 → 現行本文の取得・適合確認 → 実行先を固定 → 主Playbookに従って実行・検収 → 既存案件への成果／再開情報の保存・読戻し（可能な場合） → 結果と次の一手`。山歩きの検索は本文の指示どおり**YAMAP先行**であり、この入口を理由に観光・交通の並列検索を先行させない。個人KBに同じ目的の**優先適用手順**が設定されていれば、実取得してその適用範囲を優先する。

**状態の区別**：山歩きPlaybookは利用者採用の試用可能なActive、チャット引継ぎPlaybookは**利用者採用の共通試用**で、機械可読の[カタログ](catalog.json)に合わせて**公開参照項目7件**（試用と利用者採用Activeを含む）を登録しました。ただし正式配布 `items` は0件、`distribution_ready=false`です。独立コールドスタート試験・公開審査が済んだ正式Active配布ではなく、自動インストール／新規チャットでの自発的発見も保証しません。

**人間操作を伴うPlaybookのガイド候補（既存索引内の目印）**：**【人間用ガイドあり】Cloudflare／MCPのChatGPT初回接続**は[操作ガイド](guides/cloudflare/mcp-chatgpt-first-connection.html)を参照。AIがAPI経由で実行できるWorkerのデプロイ・Secret管理を人間に押し戻さない。**【人間用ガイド検討・条件付き】初回APIトークンの権限設定・WordPressアプリパスワード・環境固有の複数画面操作**は、その場の1操作案内と既存公式資料で足りない場合だけ候補とする。既存YouTube初回認証ガイドを複製しない。**ガイドを使ったAIへ**：トラブルで実画面・スクリーンショットから古い操作説明を発見し、本人の問題解決後に共有可能な具体的差分があれば、一度だけ**任意のガイド修正PR**を提案する。GitHub接続と本人の共有意思がある場合はAIが作成を引き受け、権限不足なら既存Issueへ切り替える。画像の秘密・個人情報、再掲載許可を確認し、**PRの作成とマージを混同しない**。改善提案は通常利用者の必須タスクではない。詳しくは[開発プラクティスのガイド改善出口](docs/DEVELOPMENT_WORKFLOW_PRACTICES.md#人間向けガイドブックの改善に参加できる出口2026-11-18-本人採用)を正本とする。

**自由投稿と利用時の選定は別**：誰でも従来の `[共有]` Issueへ投稿できる。外部PlaybookやMCPを使うか判断するときだけ[AD&C純正のサードパーティ選定Playbook](skills/third-party-selection/SKILL.md)を参照する。投稿を審査制度・AD&C公認・正式カタログへの自動登録と混同しない。

## AD&Cの理念との関係

**どんな玄人も、専門外では素人だ。** AD&C（AI-DODAI & Continuity）は、分野の玄人が当然知っている基本知識・手順・判断基準を共有できる形で整え、AIが利用者の状況に応じて案内することを目指します。**玄人の「当たり前」はAIが案内。人間は、その先の判断に集中する。**

人間の判断を置き換えたり、誰もが専門家になれると約束したりするものではありません。出典・反論・適用条件・更新状況を示し、重要な選択と承認は本人に残します。正式配布カタログのActive項目は現在0件ですが、公開参照項目は6件（試用・利用者採用Activeを含む）あります。理念全体の実装・効果が検証済みという意味ではありません。

## 何をしようとしているか

一から大量の情報を調べなくても、主要な主張、支持・反対の理由、未解決点、関連する専門家の実際の見解へ到達できる比較資料を育てます。答え・勝者・推奨行動の提示は必須にしません。個人差と科学的知識の更新を前提に、異論や判断が分かれる条件を残します。

- 確立した知見だけでなく、有力な仮説も根拠・不確実性・リスクを区別して扱う。
- 人気や投稿数を正しさとせず、出典の質・独立性・反証・適用条件を確認する。
- 主張ごとに専門家の公開発言・論文を紐付ける。発信者、監修者、相談先を区別し、必要時だけ本人に合う候補を検討する。
- 誤りは訂正し、重大な問題は撤回する。古い版を利用している人にも追跡可能な記録を残す。
- 最終的な選択は本人が行い、結果を保証しない。妥当な判断過程と偶然の成功を区別する。
