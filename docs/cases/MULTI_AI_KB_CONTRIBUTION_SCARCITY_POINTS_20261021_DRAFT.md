# 外部AIとの対話を共有KBの提案へつなぐ事例：希少性ポイント（Draft）

- 記録日：2026-10-21
- 状態：**Draft / 未審査事例**。正式な共有知 `claim_map`、`playbook`、Active項目ではない。
- 関連分野候補：`organization-governance`（分野メニューは[Draft PR #9](https://github.com/Yosio-DMZ-C/AD-C-Shared-Knowledge/pull/9)で提案中。現行mainで正式採用済みとは扱わない）
- 用途：(1) 組織づくりの制度仮説を保持する、(2) **一般利用者が自分のAI経由でGitHub共有KBへ提案できるか**の実例とする。
- 記録の起源：利用者がGrokとの議論を任意に別のAIへ持ち込んだ。原会話の全文、個人情報、外部AIの発言の逐語転載は含まない。下記は提案の独立した再構成であり、Grokの返答を独立の科学的根拠とは数えない。

## 1. なぜこの事例を保存するか

理想とするAD&Cの貢献導線は「GitHubやMarkdownを知らない人でも、自分のAIに『このアイデアを共有KBへ提案して』と頼めばよい」というもの。

今回、**人間 → Grokとの議論 → 人間による内容の持ち運び → 別のAIによる現行KBとの照合 → GitHub上のDraft提案**という一連の流れを試した。異なるAIの自動通信や、任意のAIからの無条件の投稿成功を証明した事例ではない。

目的は結論を確定することではなく、よい着想・反論・未検証点を**個別AIや個人の会話だけに閉じ込めず**、他者が再検討できる形に変えること。

## 2. 元の着想（仮説）

対象：少人数の任意参加型の知的コミュニティや共同プロジェクト。金銭的報酬・人事評価とは切り離した**遊び心のある貢献可視化**。

- タスクは募集前に十分細かく分割し、着手条件と完了条件を理解可能にする。小さい単位で自発的に協力できる状態が前提。
- 全員に立候補の機会を与え、**立候補者が少ないタスクほど基本ポイントが高くなる**。例：10人の関係者で1人だけ立候補なら10点、5人なら2点、10人なら1点。これは価値の正確な定量評価ではなく、立候補の希少性を表すゲーム上の仮説。
- **一番槍**：他者が引き受けない必要な仕事に手を挙げたこと自体に価値を認める。実行の調整や協力者選定の相談に先んじるが、他人の参加拒否権や審査免除を意味しない。
- 立候補・実行着手と完了の**2つの局面**を評価し、途中参加して分担した場合は所定の総ポイントを分ける。誰も参加できない場合、タスクの条件・粒度・見積もり等を見直して**再度全員へ公募**する。
- 正式な功績・クレジット、採否の権限、報酬・権利と、ゲーム用ポイントを混同しない。多数決・人的判断・AIによる任意の表彰案は独立して検討する。

### スクラムとの関係と条件

[Scrum Guide 2020](https://scrumguides.org/scrum-guide.html)は、スプリントバックログの項目を開発者がしばしば1日以下の作業単位へ分解し、状況に応じて計画を適応させると記す。**必ず十分細かく分割済みになる保証**、あるいは**再分割はすべて見積もり失敗**という規則ではない。実務上は、タスクの分割・再募集を手戻りとして記録して改善することと、未知の発見への正常な適応を区別する。

### 未決定・反例候補

- 定式化：10人を超える時の正規化、整数丸め、1件の開始・完了合計の上限10点か各段階10点か、分割時の端数処理は**未確定**。
- 挙手人数と必要性・難度は別。人気のない**不要な仕事**に高得点を付けないため、そもそものタスク妥当性を事前確認する必要がある。
- 仲間内の挙手調整・談合、タスクの過度な分割、完了品質の低下、協力者間の不公平、目立たないレビュー作業の過小評価。
- 開始時の点数が未完了のまま確定する場合の扱い。ポイントが公式の意思決定権や報酬に転用された場合の副作用。
- **「立候補を見送っても本人の点数は増えない」は、他人の点数を増やす談合や戦略的な協力抑制を防ぐ証明ではない。**
- ゲーミフィケーションとして楽しいか、実際に引受率・完了率が改善するかは未検証。

**現時点の位置付け**：C07（希少性ポイント）を中心に、C03（明示的クレジット）、C04（人間の決定）、C05（AIの補助的表彰）を比較する将来の`claim_map`候補。出典未確認のまま「定石」や「推奨手順」に昇格させない。

## 3. 共有KBに参加するための最小導線（設計仮説）

利用者に求める言葉の例：

> このAIとの議論で共有する価値がありそうなアイデアを、AD&Cの共有KBへ提案して。個人情報や会話全文は公開せず、必要なところだけ私に確認して。

利用者がGitHubの用語を知っている必要はない。AI側で次の順に処理する：

1. **既存KBを確認**：対象の分野ID・類似事例・claim_map・審査規則を読み、重複・既存論点への差分を探す。
2. **提案を再構成**：着想、既存知識、未検証の推測、反例、実験方法、権利・機微情報を分離。元のAIがそう述べたという事実と、主張が正しいという判断は別。
3. **公開内容を本人に確認**：公開が意図されたか、出典・第三者権利に問題がないか、公開してよい要約の範囲を確かめる。許諾のない会話全文は載せない。
4. **既存GitHub機能で提案**：接続と権限がある場合だけIssueまたはDraft Pull Requestとして書き込み、投稿先を読戻す。**mainへ無断マージせず、Activeへ自動昇格させない**。
5. **人間・他AIの審査へ**：追加の一次資料、反論、試験結果を持ち寄り、既存[ガバナンス](../GOVERNANCE.md)の範囲で採否判断。
6. **接続がなければ**：再利用できるMarkdownを渡して「未投稿」と明記する。投稿したと偽らない。

主な既存契約：[貢献方法](../../CONTRIBUTING.md)／[基本設計](../ARCHITECTURE.md)／[主張比較テンプレート](../../templates/CLAIM_MAP_TEMPLATE.md)。別種の正式kind、新サービス、GitHub専用UI、新DBはこの事例には不要。

## 4. 今回できたこと・まだできていないこと

- **PASS候補：** 別AIでの議論結果を人間が運び、他AIが設計を照合したこと。GitHubのDraft提案が作成された場合は、そのURLと実際のファイル読戻しを別途確認する。
- **NOT_RUN：** 不特定の他利用者・他AIからの独立投稿、誰でも利用できるインストール済み投稿機能の検証、実際のポイント運用、参加者の行動改善、専門レビュー。
- **採否待ち：** この事例を将来の正式な組織づくり`claim_map`の調査素材として使うか、AI経由のGitHub投稿をAD&C一般利用の公式フローにするか。どちらもこの事例の登録だけで確定しない。

## 5. 将来の最小試験

新規参加者1名が、好きなAIと議論した**架空のアイデア**を持ち込み、「共有KBへ提案して」と一度頼む。本人の公開承認後、AIが既存KBと照合しGitHub Draftへ保存、別途読戻しする。必要な手入力・行き詰まった操作・投稿までの時間を測定する。Grok、ChatGPT等の製品横断で少数回試す。

評価すべき成果は**投稿件数やAIの華やかな説明ではなく、利用者がGitHub操作をほぼ意識せず、自分のアイデアを安全に審査待ちへ届けられたか**。
