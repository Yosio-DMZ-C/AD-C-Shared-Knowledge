# 開発調査の共有プラクティスとプロジェクト進行スタイル

- 版：0.1.4（2026-10-29：担当の承認済み実装完走とリーダー横断監査の役割境界を整合。v0.1.3を維持）
- 状態：**共有KBの運用ルールとして公開。個別SkillのActive認定ではない**
- 対象：開発調査、実装支援、KB整備、成果物レビュー
- 上位の進行契約：[AgentOS-C本体の共通標準](https://github.com/Yosio-DMZ-C/AgentOS-C/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)。本書は共有KBで利用する具体化であり、個人KBの非公開内容を共有へ移さない。

## 1. 先人の定石を、利用者の通常作業へ埋め込む

1. **基本作法**：正式ソースの個別リンク、形式・拡張子・文字コードの整合、既存ファイル・IDの維持、差分、バックアップ、保存後の検査。
2. **開発の定石**：明確な成功条件、公式仕様と過去の検証の再利用、まず1案、最小変更、関係する機能だけの試験、失敗時の復旧、ADRによる重要な決定履歴。
3. **個別の判断**：費用・価値観・権限や利用上の許可は本人の領域。一般的な経験則だけで、実際の機密性・安全性・適合性を保証しない。

目的は利用者の質問の品質に依存せず、専門家が知っている失敗予防を最初から適用すること。巨大なフレームワークの無条件採用やチェック項目の増殖は避ける。

### 書式契約の置き場所：人間の原則 → 専門Playbookの検査（β・2026-10-31）

**原則は人間が判断・レビューするための短い説明**にとどめる。厳密な納品書式（ファイル名、固定フィールド、順序、ZIP内の実体等）は、その成果物を扱う**既存の分野別Skill／Playbookのテンプレート・検査ツール**が正本を持つ。AIへの長い注意書きの重複を増やさない。

1. **作る直前**：該当Playbookの現行テンプレート／許可済み原本を実取得し、可変部分だけ埋める。入手できない形式を再現できたと宣言しない。
2. **渡す直前**：該当Playbookの機械検査（例：構文・アーカイブ・固定フィールド・参照名一致）を実ファイルへ実行し、不一致はその箇所だけ修正する。検査失敗・未実行なら書式PASSとしない。
3. **効果の区別**：形式検査PASS、対象環境での動作PASS、利用者の受取・実用PASSを別判定にする。既存Q1〜Q4へ結果を記録し、新しい共通チェッカーや台帳を乱立させない。

最初の実装例は[開発調査SkillのOneShot共有Draft](../skills/development-research/standards/OneShot_Standard_v1.md)を参照。個人側の正本・承認範囲を置き換えるものではない。形式遵守率と修正負担が改善したかは未実測であり、見直し時に短く確認する。

### 開発・調査の初動：先行事例と定石を確認する（β・2026-10-27）

「調査」「開発」「自動化」「ツール作成」「不具合対処」を依頼されたら、まず目的・成功条件を短く整理し、**本調査・設計・実装へ進む前に、当該分野で既に知られている解法・失敗例・実務上の定石を必要量だけ確認する**。利用者が指定した手段を最終目的と混同しない。単純な質問・軽微修正に長い調査を強制しない。

1. **先に探す**：既存KB・過去のADR／実績・手元の道具 → 公式仕様／FAQ／サポート情報 → 信頼できる業界標準・既製品・OSS・同種の成功／失敗事例。技術だけでなく、その分野固有の実務・利用者の操作・運用事例も候補にする。
2. **成立条件と反例を確認**：根拠の日付、対象サービス／OS／版／地域、利用規約、権限、データ量、実際の成功範囲を区別する。記事の手順や人気の案を、現在の環境での動作保証に読み替えない。既存方式の弱点と見落としやすい境界を確認する。
3. **最小の進め方を選ぶ**：既製機能で済むなら自作しない。調査依頼なら既知・争点・未確認を分け、次の本調査を絞る。開発依頼なら実行可能性が最も不確かな境界を小さく先行検証してから設計・実装する。人間の操作・保守・復旧負担を含めて原則1案を選ぶ。
4. **調べすぎず進む**：既存資料に十分な根拠があれば影響差分だけ照合し、毎回ゼロから検索しない。前例が見つからない場合は「未確認」と明記し、可逆な最小試験から進める。重要な採否理由と出典だけを既存案件記録に残し、追加の台帳・長文レポート・都度承認を標準化しない。

例：写真サービス間の移行では、年代別の集計結果だけを前提にコードを書かず、公式の写真取得・メタデータ・重複処理の制約と同種の移行事例を確かめ、少量の実測データで件数と取得経路を照合してから方式を決める。例は一般化した検証手順であり、個人写真や非公開ファイルを共有KBへ保存しない。

参照：[Microsoft Azure Well-Architected（成熟した既製ツールの優先）](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/tools-processes)、[Google Documentation Best Practices（最小で新鮮な文書と重複回避）](https://google.github.io/styleguide/docguide/best_practices.html)。両者が本βの具体的な4手順を定めているという意味ではない。

### 調査担当からリーダーへの引継ぎ

開発調査チャットは調査・切り分け・比較・改善候補に加え、**本人が明示承認した担当範囲の低リスク・可逆な小変更について、変更前保全・競合確認→正本／参照・必要なGit反映→読戻しまで担当できる**。提案・PRだけで終えず、進行を止める真の境界（新たな承認、公開・権限変更・不可逆処理、競合、復旧不能）を区別する。ただし、**共有ルールの正式採否・分野横断の統合判断・SkillのActive化はリーダーと既存審査が担当**し、無承認の公開mainマージ等は行わない。別チャットの自動同期は前提にせず、受信と適用を別判定する。引継ぎには[軽量テンプレート](../templates/DEVELOPMENT_RESEARCH_HANDOFF_TEMPLATE.md)を使用し、長い詳細レポートは必要な場合だけ付ける。

同一エラーの追加試行は「新しい情報を得られるか」「再試行が安全か」「人間の手戻りや有料実行を増やさないか」で判断する。権限と接続ツールの操作能力、コネクタとクラウドブラウザの認証状態は別に確認する。単発のUI操作は人間への切替も選択肢とする。参考：[Work→Google認証の調査事例](cases/WORK_GOOGLE_AUTH_FAILURE_20261014.md)、[予防KB](DEVELOPMENT_FAILURE_PREVENTION_KB.md)。

## 2. 証拠レベル・検査名

|種類|言えること|言えないこと|
|---|---|---|
|仕様の照合|特定版・プランの公式仕様には記載がある|接続中のAIから実際に実行できる|
|小規模スモーク／統合テスト|架空の1件を今回の実接続で読書きできた|Consumer/Provider契約全体、他プラン、長期同期がPASSした|
|Consumer/Provider契約テスト|通信メッセージ・APIの期待が双方で満たされる|データの意味、個人情報の保護、業務運用の正しさ|
|構造・静的検査|形式、参照、必須キー、危険な公開文字列等を確認|本番での稼働、機密情報の完全な非漏えい|
|用途適合レビュー|本人の目的・安全・規制等への適合を検討|規制への法的適合をAIが単独で保証できる|

実施状態はPASS / FAIL / NOT_RUN / N/A（理由付き）で管理し、**必須検査のFAIL・NOT_RUNは完成を停止**する。途中で作成した記録はDraftとして保存し、未検証部分を事実として再利用しない。

## 3. 承認待ちでも進めるためのモード

`project_execution_style` に `continuous`（自動継続・推奨）／`checkpoint`（大きな節目で確認）／`stepwise`（都度確認）を持つ。初回または変更が必要な時に一度だけ選択肢を示す。現在の依頼に継続指示があれば、その依頼の範囲で適用し、毎工程で聞き直さない。

- 未確認の選択が作業の一部だけに関係する場合、**その枝だけdefer/block**し、承認済みの調査・下書き・静的検査・独立作業を進める。
- 権限変更、公開、外部送信、購入、削除、重大な本番上書き、機密データの操作には個別承認。継続モードでも越えない。
- 各案件の最後に**変更・根拠・検査結果・未完了・質問**を一括提示し、推奨と未承認の操作を混同しない。
- 約30日ごとに、活動中案件の通常のやり取りの中で「現在のスタイルでよいか」を一度確認する。自動通知やバックグラウンド監視を行うには別途設定が必要。回答待ち中でも既存の許可範囲を超えずに続ける。

### 成果物リンク・取得の基本作法

ファイルの**作成**、外部サービスへの**保存と読戻し**、個別URLの**対象確認**、利用者端末での**実ダウンロード**は別々の状態として検査する。単に `sandbox:` 形式のリンクを出したり「お気に入りに登録」が表示されたりしても、端末への保存成功とは言えない。リンクに問題があれば同じ経路を繰り返さず、本人が許可した非公開保存先の個別リンクまたは実際に使える別形式を用意する。受取確認がない限り端末DLは `NOT_RUN`、失敗報告があればその経路を `FAIL` とする。公開ACLの変更は実行しない。

**文末のコピー用表示**：短いMD・スクリプト・指示文（目安4,000文字まで）は、可能なUIで全文をコピーできるブロックを回答末尾に置く。長文は保存・読戻し確認済みの**個別ファイルリンクを主経路**とし、末尾には短い再利用用指示のみ置く。省略・抜粋であることを表示し、全文が必要なら分割して提示する。利用者がクラウド経由の受取成功を報告した場合、その経路だけをPASSに更新する。

詳細な品質ゲートと公式ヘルプは[本体の共通標準](https://github.com/Yosio-DMZ-C/AgentOS-C/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)に置き、同じ文章を各Skillへ重複展開しない。

## 4. 共有KBの記録方法

重要判断は短いADRとし、ID・判断日・目的・比較候補・採否・一次URL・未検証・再確認条件を持たせる。採用／却下／保留・撤回を記録し、理由なく古い判断を上書きしない。

通常のSkillや共有項目のActive化は既存の[更新・審査・撤回規則](GOVERNANCE.md)を優先する。**自動継続モードは、必要な人間レビューの省略や未完了ゲートのPASS化ではない。** 独立レビュー待ちなら、その手前の作業完了・Draft保存・次のレビュー準備までをAIだけで進められる。
