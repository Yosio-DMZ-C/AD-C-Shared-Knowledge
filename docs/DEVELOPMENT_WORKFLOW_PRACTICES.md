1. **基本作法**：正式ソースの個別リンク、形式・拡張子・文字コードの整合、既存ファイル・IDの維持、差分、バックアップ、保存後の検査。

目的は利用者の質問の品質に依存せず、専門家が知っている失敗予防を最初から適用すること。巨大なフレームワークの無条件採用やチェック項目の増殖は避ける。

### 開発・調査の初動：先行事例と定石を確認する（β・2026-10-27）

「調査」「開発」「自動化」「ツール作成」「不具合対処」を依頼されたら、まず目的・成功条件を短く整理し、**本調査・設計・実装へ進む前に、当該分野で既に知られている解法・失敗例・実務上の定石を必要量だけ確認する**。利用者が指定した手段を最終目的と混同しない。単純な質問・軽微修正に長い調査を強制しない。

1. **先に探す**：既存KB・過去のADR／実績・手元の道具 → 公式仕様／FAQ／サポート情報 → 信頼できる業界標準・既製品・OSS・同種の成功／失敗事例。技術だけでなく、その分野固有の実務・利用者の操作・運用事例も候補にする。
2. **成立条件と反例を確認**：根拠の日付、対象サービス／OS／版／地域、利用規約、権限、データ量、実際の成功範囲を区別する。記事の手順や人気の案を、現在の環境での動作保証に読み替えない。既存方式の弱点と見落としやすい境界を確認する。
3. **最小の進め方を選ぶ**：既製機能で済むなら自作しない。調査依頼なら既知・争点・未確認を分け、次の本調査を絞る。開発依頼なら実行可能性が最も不確かな境界を小さく先行検証してから設計・実装する。人間の操作・保守・復旧負担を含めて原則1案を選ぶ。
4. **調べすぎず進む**：既存資料に十分な根拠があれば影響差分だけ照合し、毎回ゼロから検索しない。前例が見つからない場合は「未確認」と明記し、可逆な最小試験から進める。重要な採否理由と出典だけを既存案件記録に残し、追加の台帳・長文レポート・都度承認を標準化しない。

例：写真サービス間の移行では、年代別の集計結果だけを前提にコードを書かず、公式の写真取得・メタデータ・重複処理の制約と同種の移行事例を確かめ、少量の実測データで件数と取得経路を照合してから方式を決める。例は一般化した検証手順であり、個人写真や非公開ファイルを共有KBへ保存しない。

参照：[Microsoft Azure Well-Architected（成熟した既製ツールの優先）](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/tools-processes)、[Google Documentation Best Practices（最小で新鮮な文書と重複回避）](https://google.github.io/styleguide/docguide/best_practices.html)。両者が本βの具体的な4手順を定めているという意味ではない。

### ツールの1入口・発見可能性・創造性（正式運用／2026-11-01採用）

**原則**：独立して再利用するツールを作成・重要改訂した場合は、**人間とAIの両方が読める自然言語の1実行入口を必ず用意する**。コードで固定できる処理は適切な実行環境で機械化し、創造性を必要とする工程は自然言語の適切な裁量を残す。これは本体[共通実行標準 §6.3.2〜§6.3.3](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)の「1タスク1実行正本・必要資料/素材/ツール欄」の具体化であり、新しい並行台帳・独立検収ゲートではない。

1. **実行物の近くに1つの使い方**：リポジトリ／既存実行キット内の`README.md`または既存の現行Runbook等から、何のため・使い所／対象外、対応OS・権限と依存条件、入力、実行入口1つ、出力先、失敗時の停止・再開、取得先・版・採用状態、確認済み/未確認の範囲が分かること。短い単独CLI・既存製品UIで足りる場合は、既存案内を実行入口に指定し、重複のREADMEやランチャーを増やさない。
2. **双方向に発見できる**：既存Playbook/Skillの「必要資料・素材・ツール」欄で使う工程と自然言語入口を結び、既存の`registry`／Project・Area Context／開発Skillの「道具棚」から**目的の自然文でも**到達できるようにする。実体を正本とし、手順全文を各所へ複製しない。案件固有の判断が必要な場合はカスタムPlaybookへつなぐが、既存正本だけで完結するなら増設しない。
3. **機械化は適材適所**：ファイル選択、固定文字列、公式素材の非生成合成、サイズ、ハッシュ、構文検査、CI等の決定論的工程は`.py`／`.ps1`／`.sh`／既存ワークフロー等で固定できる。Pythonは必須としない。デザイン、構図、文章表現などの創造的工程は目的・禁止事項・評価条件を自然言語で指定し、方法の幅を維持する。機械検査PASSと人間による作品評価は別判定。
4. **完了時の接続検収**：ツール実体と1入口を読み戻し、Playbookと道具棚のリンクから現行版・状態を一意に確認する。対象環境での実行結果、別AIの自然文からの発見・再利用はそれぞれ確認できた場合だけPASS。未実施は`NOT_RUN`。既存のQ1〜Q4を使い、チェック票や新DBは作らない。Draft/PR/研究中を正式版や`main`実装済みと誤記しない。

**採用の根拠と境界**：2026-11-01、利用者が原則の正式運用を明示承認。サムネイルCASE Aの「AIが背景・見出しの表現を創作 → Pythonが公式素材を原本合成 → 実物を検査」が具体例。ただし当該CASE Aの凍結原本と個人KBの非公開実体は変更しない。ツールの使い勝手や別AIの自動発見が実証済みという承認ではない。個別SkillのActive化・公開カタログ掲載は引き続き既存[更新・審査規則](GOVERNANCE.md)に従う。

### AD&C Playbook共通標準｜今後の作成・改訂の既定（2026-11-11 本人正式採用）

**採用範囲**：これから作成するPlaybookと、今後変更する既存Playbookの**変更対象部分**に適用する。既存Playbook・個人KB・動画/サムネイルの自動一括書換え、既存案件の新規起票、追加の常時監視や開始ゲートは行わない。新設・実質改訂時には本書の規約を引き継ぐ。一般利用者にはコード実行・SHA計算を要求しない。

- **二重インターフェース**：人間向け日本語Playbookを目的・制約・工程・判断理由の正本として保持。機械的に確定できる検索経路、条件分岐、選択肢ID、遷移先、形式検査はPython/既存の同等部品を活用し、将来はPythonに段階的に統一する。説明・文言・意味解釈はAIが日本語本文と状況から都度生成する。機械で意味を自動証明しない。
- **UI責任の分離**：Pythonはナビの**論理構造**まで。ChatGPT等で押せるボタンの描画・文言・押下・送信は各AIのUI/権限を使い、ボタンがなければ番号付き日本語選択肢を出す。生成や表示を送信完了と誤認しない。
- **入口・パス**：Playbookの上部は既存テンプレートと同じ `編集時の3参照 → カスタム手順書の優先分岐 → AI_NAV_PY_PATH → 日本語本文`。相対パスは当該Playbookが存在するディレクトリから解決。実在するナビだけ指定し、未実装は `NONE`、動画/サムネイルの創作例外は `CREATIVE_EXEMPT`。Python環境がなくても日本語案内は使える。パスは自動実行許可ではない。
- **改訂時の差分検出（共通の既定）**：変更前の**検証済み正本（Gitの親版・保存済み前版）**と変更後の実ファイルを取得し、SHA-256と日本語本文の差分を比べる。対象にナビ/Pythonがあれば、差分の影響を受ける条件・行動ID・遷移先だけ整合させ、対象限定で再検査・読戻しする。**ハッシュ不一致は変更の発見であり、誤りや意味不整合の証明ではない**。旧正本がないときは `BASELINE_UNAVAILABLE` と記録し、無関係な許可済み実務は継続する。日本語原文を機械出力で無断上書きしない。
- **既存ツールへの接続**：専用 `runner.py` は `--expected-sha256` と `--baseline` がある**単一AUTO領域**のみを保護する。一般のPlaybook本文には、新設の**読取専用** [check_playbook_diff.py](../skills/markdown-auto-pilot/check_playbook_diff.py) を `python check_playbook_diff.py --baseline <変更前.md> <変更後.md>` で使える（パスは例示）。対象が `## AI execution appendix` を1つ持つ場合はその前を日本語領域として比較し、それ以外は全文を比較する。出力の `CHANGE_DETECTED` は**差分発見**であり、全業務停止ではない。Python不可ならGitの差分と版履歴で同じ対象を確認する。ツールは自動修復・意味解析・常時監視をしない。
- **創作の明示例外**：**動画・サムネイルの創作工程**には今は適用しない。作品固有Runbook、採用済みCASE A、生成プロンプト、確定構図・素材・音声・文字や既存制作順序を無断変換・再生成しない。既存のサイズ計測・非生成合成・検査ツールは継続使用可能。早期統合は既存PR責任者との比較・独立試験・本人判断が済んだ対象だけ進める。例外の解消は今後の課題だが、**例外があることを理由に一般Playbook標準の採用を止めない**。

**最小運用**：更新前を保全 → 実際に変更 → 差分/SHAを確認 → 必要な機械定義だけ同期 → 対象範囲の実検査・Git保存・読戻し → 未検証はそのまま既存案件へ記録。新しい必須の報告書・DB・全件CI・本番停止規則は作らない。

- **人間にも理解・改良できる入口（該当時）**：AIが発見・選択・取得・実行できるだけでなく、利用者が日本語で**目的／いまの段階／判断する箇所／結果と再開方法**を必要な深さだけたどれるよう、既存のPlaybook本文・ワークシート・操作画面に短い説明と参照先を置く。コードや画像だけを唯一の入口にしない。学びたい人が手順の理由や改善先へ進める一方、**便利に使って終える人には長文読解・知識共有・GitHub操作を課さない**。個人情報を共有KBへ移さず、既存の専門Playbookと採用済み制作工程を優先する。背景は[既存Designer’s Noteの二重インターフェース](../templates/DESIGNER_NOTE.md)に保存。
- **人間とAIの認知差を埋めるナビ**：AIが理解しやすい文章・URL・状態名と、人間が判断に使う画面の配置・見えている範囲・押せる場所・直前の操作は同一ではない。迷いや誤操作が生じ得るUI・サイト・手順の制作や案内では、①実際に人間が目にする画面・隠れた要素・現在位置、②次に行う具体的な操作と代替経路、③操作後に確認できる結果を、原画面・Playbook・ワークシートの該当部分で結ぶ。表示・クリック・保存・相手の受領は別状態として扱い、見えていない要素や未実行の成功を推測しない。これは**必要な場面で呼ぶ設計機能**であり、全作業に3項目の報告・追加承認・事前検査を義務付けるものではない。
- **軽い実地確認**：完成した実物が使えるか、必要な入口から辿れるか、依頼された操作が動くかを対象範囲で確かめる。変更しなかった機能の網羅再検査は原則しない。未実施をPASSとは言わず、結果と未完了を短く残し、横断的な不整合は既存リーダー巡回で事後修正する。

**適用の解釈**：旧規則のうち、全員・毎回の「事前3巡・全ワークシート記入・全SHA連鎖・重複承認」を要求する一般条項は、実務を止めるために使わない。危険な操作の必要な確認、明示指定された検査、既存の専門Playbookの機能・設計ノートは削除しない。新しい検査・工程を増やす前に、既存の機能を活用する。

### 最終ゴールと必要な承認を人間に見せる（2026-11-08）

作業を小さく分けることと、依頼の最終到達を小さく切り下げることは別。実行できる工程は完走し、必要な権限を越える最後の操作（例：mainマージ・公開）が残れば、**「何をすれば終わるか／実行済みか／何を承認するか」**を一目で伝え、UI対応時はクリック可能な承認ボタンを示す。設計・Draftだけで「完了」と肯定的にまとめない。承認済みの仕事に余分な確認を足さない。低リスク・可逆な試験は最終形を先に試し、エラーを最小修正し、必要時に戻す。[標準コミュニケーション Playbook](../skills/communication-navigation/SKILL.md)へ詳細を集約し、他の専門Playbookに同じ長文を複製しない。

### Playbook作成・更新の実装仕様｜軽い承認ボタン継承（2026-11-08）

**ユーザー向けの違いは「AD&Cで必要なときに承認ボタンが出る」だけ**に抑える。新しい承認境界がある時は、今回の最終ゴール・残操作を一言で示し、実際に動く承認ボタンを出す。ボタンが無い環境なら **「最終ゴールへの承認指示文」→ `text`コードブロック → 「これをチャットに投入いただければ実施します。」** を同じ位置に表示する。本人がすでに承認した作業で再度止まらない。

**新規Playbookを作るとき**：[既存テンプレート](../templates/PLAYBOOK_TEMPLATE.md)から共通の実動ボタン／「もう一声」／承認導線への**1行参照を既定で継承**する。**既存Playbookを更新するとき**：既存の1行参照があれば維持し、なければ**実際の改訂対象として必要な場合にのみ**追加する。新規既定を理由に既存Playbookを一斉改訂しない。共通仕様は[標準コミュニケーションPlaybook](../skills/communication-navigation/SKILL.md)の1か所に保持。専門の独自UI・入力待ち・ボタン0件を優先する。特に**サムネイルの制作順・画像生成指示・確定素材には混入させない**。動画制作側はPR検討が終わるまで現行方式に触れない。共通ボタンは制作物そのものではなく対話の操作導線。チェックリスト・長文・独立DBを増やさず、UI非対応なら短い返信文やコードブロックで代替し、実動ボタンがあるふりをしない。安全・人命・不可逆・公開等の境界を維持する。

### 複数AI・共同開発者のGit提出（AD&C現行はリーダー経由）

共有KBへの提案は、GitHubに接続できるAIなら将来的に直接提出できる設計を維持し、利用者を特定のAIへ戻すことを要件にしない。ただし**現在のAD&CにおけるMuseからの提案は、開発リーダーが受領して必要なPRを提出・判断する**。GitHubへのADMIN認証だけでMuseの直接PR発行・main書込を有効化しない。複数担当の競合確認・同一対象の再利用・変更前SHA・局所復旧・機密非公開・相互参照・受領と採用の分離は[本体の共通実行標準](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)を適用する。別AIでの同時編集実験はNOT_RUN。

### 調査担当からリーダーへの引継ぎ

開発調査チャットは調査・切り分け・比較・改善候補に加え、**本人が明示承認した担当範囲の低リスク・可逆な小変更について、変更前保全・競合確認→正本／参照・必要なGit反映→読戻しまで担当できる**。提案・PRだけで終えず、進行を止める真の境界（新たな承認、公開・権限変更・不可逆処理、競合、復旧不能）を区別する。ただし、**共有ルールの正式採否・分野横断の統合判断・SkillのActive化はリーダーと既存審査が担当**し、無承認の公開mainマージ等は行わない。別チャットの自動同期は前提にせず、受信と適用を別判定する。引継ぎには[軽量テンプレート](../templates/DEVELOPMENT_RESEARCH_HANDOFF_TEMPLATE.md)を使用し、長い詳細レポートは必要な場合だけ付ける。

同一エラーの追加試行は「新しい情報を得られるか」「再試行が安全か」「人間の手戻りや有料実行を増やさないか」で判断する。権限と接続ツールの操作能力、コネクタとクラウドブラウザの認証状態は別に確認する。単発のUI操作は人間への切替も選択肢とする。参考：[Work→Google認証の調査事例](cases/WORK_GOOGLE_AUTH_FAILURE_20261014.md)、[予防KB](DEVELOPMENT_FAILURE_PREVENTION_KB.md)。

## 2. 証拠レベル・検査名

|種類|言えること|言えないこと|
|---|---|---|
|仕様の照合|特定版・プランの公式仕様には記載がある|接続中のAIから実際に実行できる|
|小規模スモーク／統合テスト|架空の1件を今回の実接続で読書きできた|Consumer/Provider契約全体、他プラン、長期同期がPASSした|
|Consumer/Provider契約テスト|通信メッセージ・APIの期待が双方で満たされる|データの意味、個人情報の保護、業務運用の正しさ|
|構造・静的検査|形式、参照、必須キー、危険な公開文字列等を確認|本番での稼働、機密情報の完全な非漏えい|
|用途適合レビュー|本人の目的・安全・規制等への適合を検討|規制への法的適合をAIが単独で保証できる|

実施状態はPASS / FAIL / NOT_RUN / N/A（理由付き）を区別する。**重大な安全・権限・不可逆操作、または本人が明示した今回の必須条件のFAIL・NOT_RUNは、その対象の完成判定を止める。** 任意・将来環境・未対象の検査はOPENとして残し、独立した安全な実務まで止めない。途中成果を保持し、未検証部分を事実として再利用しない。

## 3. 承認待ちでも進めるためのモード

`project_execution_style` に `continuous`（自動継続・推奨）／`checkpoint`（大きな節目で確認）／`stepwise`（都度確認）を持つ。初回または変更が必要な時に一度だけ選択肢を示す。現在の依頼に継続指示があれば、その依頼の範囲で適用し、毎工程で聞き直さない。

- 未確認の選択が作業の一部だけに関係する場合、**その枝だけdefer/block**し、承認済みの調査・下書き・静的検査・独立作業を進める。
- 権限変更、公開、外部送信、購入、削除、重大な本番上書き、機密データの操作には個別承認。継続モードでも越えない。
- 各案件の最後に**変更・根拠・検査結果・未完了・質問**を一括提示し、推奨と未承認の操作を混同しない。
- 約30日ごとに、活動中案件の通常のやり取りの中で「現在のスタイルでよいか」を一度確認する。自動通知やバックグラウンド監視を行うには別途設定が必要。回答待ち中でも既存の許可範囲を超えずに続ける。

### 成果物リンク・取得の基本作法

ファイルの**作成**、外部サービスへの**保存と読戻し**、個別URLの**対象確認**、利用者端末での**実ダウンロード**は別々の状態として検査する。単に `sandbox:` 形式のリンクを出したり「お気に入りに登録」が表示されたりしても、端末への保存成功とは言えない。リンクに問題があれば同じ経路を繰り返さず、本人が許可した非公開保存先の個別リンクまたは実際に使える別形式を用意する。受取確認がない限り端末DLは `NOT_RUN`、失敗報告があればその経路を `FAIL` とする。公開ACLの変更は実行しない。

**文末のコピー用表示**：短いMD・スクリプト・指示文（目安4,000文字まで）は、可能なUIで全文をコピーできるブロックを回答末尾に置く。長文は保存・読戻し確認済みの**個別ファイルリンクを主経路**とし、末尾には短い再利用用指示のみ置く。省略・抜粋であることを表示し、全文が必要なら分割して提示する。利用者がクラウド経由の受取成功を報告した場合、その経路だけをPASSに更新する。

詳細な品質ゲートと公式ヘルプは[本体の共通標準](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)に置き、同じ文章を各Skillへ重複展開しない。

## 4. 共有KBの記録方法

重要判断は短いADRとし、ID・判断日・目的・比較候補・採否・一次URL・未検証・再確認条件を持たせる。採用／却下／保留・撤回を記録し、理由なく古い判断を上書きしない。

通常のSkillや共有項目のActive化は既存の[更新・審査・撤回規則](GOVERNANCE.md)を優先する。**自動継続モードは、必要な人間レビューの省略や未完了ゲートのPASS化ではない。** 独立レビュー待ちなら、その手前の作業完了・Draft保存・次のレビュー準備までをAIだけで進められる。
